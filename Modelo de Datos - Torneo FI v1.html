00Decisiones clave

Si solo lees una página, que sea esta. Cada punto se desarrolla más adelante.

▸ Lo que recomiendo

  • Tres tablas centrales: players (una fila por persona, para siempre), registrations (una fila por persona por edición) y matches (una fila por partido). El historial real no son los puntos: son los partidos.
  • El teléfono es la llave natural, normalizado a formato internacional (+52…). Es lo único estable que tienes de cada persona.
  • El ranking es un puntaje estático por evento: cada partido y cada logro suma (o resta) una cantidad fija que nunca se recalcula. No depende de contra quién ganaste en el futuro — se cierra en el momento.
  • Cada categoría arranca en una base distinta (Principiante 100, Intermedio 250, Avanzado 450) y los puntos se acumulan entre ediciones.
  • Los bombos salen de ordenar esos puntos por categoría y cortarlos en bandas.
  • El cuestionario se guarda en columnas tipadas con enum, no en texto libre ni en un JSON gigante.
  • La disponibilidad se guarda normalizada (una fila por bloque elegido), no como matriz. Conceptualmente es una matriz; para consultar conviene en filas.
  • Las 14 fotos de facultad y 15 de carrera NO van en la base de datos. Guardas el enum y el front resuelve la imagen.

01Identidad: el teléfono como llave

Solo tienes nombre y teléfono de cada persona. El nombre/apodo cambia, se repite y se escribe de mil formas; el teléfono es único y estable. Por eso el teléfono es tu llave natural para vincular el pasado con el presente.

Normaliza a un solo formato (E.164)

Antes de guardar cualquier teléfono, conviértelo a un formato único e internacional. Así 55 1234 5678, 5512345678 y +52 55 1234 5678 se vuelven la misma cadena y no creas duplicados.

-- guarda SIEMPRE así: '+52' + 10 dígitos, sin espacios
-- '55 1234 5678'  ->  '+525512345678'
create function normalize_phone(raw text) returns text as $$
  select '+52' || right(regexp_replace(raw, '\D', '', 'g'), 10);
$$ language sql immutable;

El teléfono entra normalizado a players.phone, que es unique.

Una persona = una fila, para siempre

La tabla players es la maestra. Cada persona vive ahí una sola vez (su phone es único). Todo lo demás —inscripciones, partidos, puntos— cuelga de ella.

✓ El merge al registrarse, en una línea

Cuando alguien llena el formulario, haces un upsert por teléfono: si el número ya existe, actualizas su apodo/facultad y recuperas todo su historial automáticamente; si no existe, se crea. Esto es lo que ya tenías pensado con "autocompletar apodo/facultad y su historial al instante".

-- al enviar el formulario: crea o actualiza la persona
insert into players (phone, nickname, faculty, career)
values (normalize_phone('55 1234 5678'), 'El Tornado', 'INGENIERIA', 'MECATRONICA')
on conflict (phone) do update set
  nickname = excluded.nickname,
  faculty  = excluded.faculty,
  career   = excluded.career
returning id;  -- este id ya trae su historial colgado

Anti-suplantación: el teléfono ES la verificación

Coincide con lo que ya documentaste y para ~40–80 personas que se conocen es suficiente: no necesitas contraseñas ni OTP. El registro nace como PRE_REGISTERED/PENDING; tú confirmas por WhatsApp cuando coordinas el pago. Si alguien usa el número de otro, el mensaje le llega al dueño real y se delata solo. Si el troleo se vuelve problema, un código de 4 dígitos por WhatsApp cierra el tema — pero arranca sin eso.

Las tablas

create table players (
  id            uuid primary key default gen_random_uuid(),
  phone         text unique not null,        -- la llave: conoces el de todos, hoy e histórico
  nickname      text not null,             -- un solo nombre/apodo; no se pide nombre completo
  faculty       faculty_code,
  career        career_code,
  email         text,
  category      category_code,                 -- banda actual del jugador
  points        int default 0,            -- ranking = base + Σ point_events (cache)
  matches_played int default 0,
  created_at    timestamptz default now(),
  constraint career_solo_fi check (faculty = 'INGENIERIA' or career is null)
);

create table editions (
  id         int primary key generated always as identity,
  name       text not null,
  slug       text unique,                    -- 'fi-2025-1', 'fi-2026-2'
  starts_on  date,  ends_on date,
  scoring    text default 'sets'           -- sólo default; el formato REAL es por categoría → matches.format
);

create table groups (
  id          uuid primary key default gen_random_uuid(),
  edition_id  int references editions(id),
  category    category_code,
  label       text,                            -- 'A','B','C'
  unique (edition_id, category, label)
);

create table registrations (
  id            uuid primary key default gen_random_uuid(),
  player_id     uuid not null references players(id) on delete cascade,
  edition_id    int  not null references editions(id),
  -- snapshot de identidad al momento de inscribirse
  nickname      text,  faculty faculty_code,  career career_code,
  -- cuestionario CRUDO (tal cual lo respondió)
  representative   boolean,
  private_training training_code,
  experience       experience_code,
  frequency        frequency_code,
  techniques       text[] default '{}',        -- {'SERVE','TOPSPIN'}; "Ninguna" = {}
  participated_previously boolean,
  prev_category    category_code,
  prev_result      prev_result_code,
  -- DERIVADOS (los calcula tu scoring; se guardan para auditoría)
  category_prov    category_code,                  -- categoría provisional automática
  category_final   category_code,                  -- ajuste manual de la organización
  requires_review  boolean default false,
  wood_paddle      boolean default false,
  -- administrativo
  status        reg_status default 'PRE_REGISTERED',
  paid          boolean default false,
  seed_pot      int,                            -- bombo asignado para el sorteo
  group_id      uuid references groups(id),
  created_at    timestamptz default now(),
  unique (player_id, edition_id),            -- bloquea doble inscripción por edición
  constraint tech_validas check
    (techniques <@ array['SERVE','CHOP','BACKSPIN','TOPSPIN'])
);

create table matches (
  id          uuid primary key default gen_random_uuid(),
  edition_id  int not null references editions(id),
  stage       match_stage not null default 'GROUP',
  group_id    uuid references groups(id),
  category    category_code,
  played_on   date,
  player_a    uuid not null references players(id),
  player_b    uuid not null references players(id),
  format      match_format not null default 'SETS',  -- cómo se jugó realmente
  sets_a      int,  sets_b int,                -- marcador CANÓNICO en sets (derivado si vino en puntos)
  points_a    int,  points_b int,              -- juego único a 12/14 ORIGINAL (histórico en puntos)
  set_scores  jsonb,                          -- [[14,9],[12,14],[14,10]] cuando hubo sets reales
  winner      uuid references players(id),
  by_default  boolean default false,        -- ¿se ganó por incomparecencia?
  pts_a_delta int, pts_b_delta int,        -- puntos que generó este partido (auditoría)
  created_at  timestamptz default now(),
  constraint distintos check (player_a <> player_b)
);

create table availability_slots (
  registration_id uuid references registrations(id) on delete cascade,
  day         date not null,
  block_start time not null,             -- 07:00, 09:00, …
  primary key (registration_id, day, block_start)
);

El libro mayor de puntos (point_events)

El corazón del ranking estático: una fila por cada cosa que da o quita puntos (un partido, pasar de grupos, ser campeón, un ajuste manual). Cada fila guarda una cantidad fija que no se vuelve a tocar. El ranking de una persona es, literalmente, base de su categoría + suma de sus eventos — nunca un recálculo relativo a rivales. Esto es lo que hace al modelo "estático" y, de paso, 100% auditable: ves de dónde salió cada punto.

create table point_events (
  id          uuid primary key default gen_random_uuid(),
  player_id   uuid not null references players(id) on delete cascade,
  edition_id  int  references editions(id),
  match_id    uuid references matches(id),       -- null si es logro o ajuste manual
  type        point_event_type not null,
  points      int  not null,                     -- FIJO; + o -, nunca se recalcula
  note        text,
  created_at  timestamptz default now()
);
-- Ranking = base de categoría + Σ(points). Nada se recalcula hacia atrás.

◆ Por qué dos niveles (player + registration)

El player es quién eres (estable). La registration es quién fuiste en esa edición: tu categoría, tu cuestionario, tu bombo, tu grupo. Guardar un snapshot del apodo y la facultad en la inscripción te deja ver el historial tal como ocurrió, aunque la persona cambie de apodo o de carrera después.

◆ Activa RLS en Supabase

Estas tablas son escribibles desde el cliente. Activa Row Level Security y deja escritura solo vía función/servicio (o políticas estrictas). Para el formulario público, expón una función rpc que valide e inserte, en lugar de dar insert directo a anon.

03Importar el historial (Sheets → BD)

Tus hojas de cálculo ya contienen el dato más valioso: cada celda de la tabla "Marcadores" es un partido. La fila de "Clasificación" (Puntos, Diferencia, a favor/en contra) se puede recalcular desde los partidos, así que no la importas: importas los partidos y la clasificación sale sola.

◆ Cómo estuvo armado el torneo pasado

Hubo 3 categorías —Principiantes, Intermedios y Avanzados— y cada una tuvo fase de grupos + fase de llaves (eliminatorias). Avanzados además tuvo un repechaje "todo o nada" para la gente que entró después de los grupos: ganas y avanzas, pierdes y quedas fuera. Eso es una fila matches con stage = 'REPECHAJE'.

Formato distinto por categoría: sólo Avanzados se jugó a sets (2-1). Principiantes e Intermedios fueron juego único a puntos (Principiantes a 12, Intermedios a 14). Desde el nuevo torneo las tres serán a sets — por eso conviene traducir el histórico de puntos a sets (siguiente bloque).

Lo que ves en la hoja

La cuadrícula "Marcadores" es una matriz round-robin. En Avanzados la celda ya es sets: 2-0, 2-1. En Principiantes / Intermedios es un juego único a puntos: 12-9, 14-8. Las llaves se leen igual, partido por partido.

Lo que guardas

Una fila en matches por cada celda de la mitad superior de la matriz (la espejo es el mismo partido). Guardas format, el marcador original (en points_a/b o en sets), el winner y el stage.

Traducir puntos → sets (para que el historial sea homogéneo)

Como ahora todo se juega a sets, los juegos viejos a puntos de Principiantes e Intermedios necesitan un marcador de sets equivalente para que el ranking de puntos y el historial sean comparables entre categorías y ediciones.

⚠ Nunca borres el marcador real

Guarda los puntos originales en points_a/points_b y deriva sets_a/sets_b. El juego a puntos es la verdad histórica; el marcador de sets es una proyección para homogeneizar. Si mañana cambias la regla, recalculas los sets sin haber perdido nada.

La regla: el margen decide 2–0 ó 2–1

Ganar el juego ya es ganar el partido, así que el ganador siempre lleva 2 sets. Lo apretado decide si el perdedor se llevó 0 (paliza) o 1 (cerrado), según el margen relativo al objetivo del juego:

  • Juego a 14 (Intermedios): margen ≥ 4 ⇒ 2–0; margen ≤ 3 ⇒ 2–1.
  • Juego a 12 (Principiantes): margen ≥ 3 ⇒ 2–0; margen ≤ 2 ⇒ 2–1.
  • Todo juego que se fue a deuce (16–14, 15–13, 18–16) tiene margen 2 ⇒ 2–1, lo más cerrado posible.

Conserva la señal de dominancia, que es justo lo que los puntos por partido (sección 6) aprovechan: una paliza 14–4 se traduce a 2–0 (+12) y un 14–12 a 2–1 (+10), igual que si se hubiera jugado a sets de verdad.

En código, una función pura:

// Traduce un juego único a puntos -> [sets de A, sets de B].
// target: 12 (Principiantes) o 14 (Intermedios)
function juegoASets(puntosA, puntosB, target){
  const margen = Math.abs(puntosA - puntosB);
  const comodo = target === 14 ? margen >= 4 : margen >= 3;
  const perdedor = comodo ? 0 : 1;          // 0 = paliza, 1 = cerrado
  return puntosA > puntosB ? [2, perdedor] : [perdedor, 2];
}
// juegoASets(15,13,14) -> [2,1]    juegoASets(14,8,14) -> [2,0]

Y el backfill en SQL sobre los partidos ya importados en puntos:

-- Deriva sets_a/sets_b para los partidos históricos jugados a puntos
update matches set
  sets_a = case when points_a > points_b then 2
                when abs(points_a-points_b) >= (case when format='POINTS_14' then 4 else 3 end) then 0
                else 1 end,
  sets_b = case when points_b > points_a then 2
                when abs(points_a-points_b) >= (case when format='POINTS_14' then 4 else 3 end) then 0
                else 1 end
where format in ('POINTS_12','POINTS_14') and points_a is not null;

◆ Las llaves que ya estaban en sets entran tal cual

Aplica la regla sólo a celdas que son un juego único a puntos. Donde el bracket ya muestra sets (2–0, o 3–2 en una final al mejor de 5), impórtalo como format='SETS' sin convertir. El campo format por partido te deja mezclar ambos en la misma edición sin ambigüedad.

Vincular el histórico: el teléfono ya lo tienes

Aquí está tu ventaja real: del torneo pasado conoces nombre, teléfono, categoría y hasta dónde llegó cada quien. No hay nombres sueltos que adivinar — el teléfono enlaza pasado y presente desde el día uno, y es justo por el teléfono que los resultados históricos se conectan con el historial y con los puntos de ranking del nuevo torneo. La carga es directa:

  1. Crea la edición pasada. insert into editions … 'fi-2025-1'.
  2. Carga un player por persona con su teléfono normalizado y su apodo. Como phone es la llave única, si esa persona vuelve no se duplica: cae sobre la misma fila.
  3. Inserta los partidos leyendo la matriz de marcadores: guarda format y el marcador original. En Principiantes/Intermedios deriva los sets (bloque anterior); en Avanzados entran tal cual. Calcula winner y, por cada partido y logro, escribe sus filas en point_events (sección 6) para dejar players.points al día.
  4. Al registrarse de nuevo, el enlace es automático. El upsert por teléfono (sección 1) encuentra a la persona; su historial, sus puntos y su categoría previa ya cuelgan de su player_id. No hay que "reclamar" ni reconciliar nada.
-- Cargar un jugador histórico CON su teléfono (es la llave)
insert into players (phone, nickname, faculty, category, points)
values (normalize_phone('55 1234 5678'), 'Luis Arturo "Fitch"', 'INGENIERIA', 'AVANZADO', 0)
on conflict (phone) do nothing;     -- si ya existe, no lo dupliques
-- Sus matches y point_events se ligan por player_id; al re-registrarse, todo aparece solo.

✓ Por qué ya no hace falta "reconciliar"

El teléfono es único en players. Cargas el histórico con teléfono y, cuando esa persona llena el formulario del nuevo torneo, el upsert por teléfono cae sobre la misma fila: recupera apodo, categoría anterior, historial de partidos y puntos de ranking al instante. La pregunta "¿jugaste antes?" pasa a ser informativa, no un disparador de búsqueda por nombre.

⚠ El único caso de fusión: una persona con dos teléfonos

Con el teléfono como llave los homónimos dejan de ser problema: dos "Luis" son dos números distintos. El único duplicado posible es que la misma persona aparezca con dos números (cambió de teléfono). Para eso dejas una fusión manual: reasignas sus matches y point_events al registro bueno y borras el vacío.

-- Fusionar dos jugadores (misma persona, dos teléfonos)
update matches      set player_a = :keep where player_a = :dup;
update matches      set player_b = :keep where player_b = :dup;
update matches      set winner   = :keep where winner   = :dup;
update point_events set player_id = :keep where player_id = :dup;
delete from players where id = :dup;

04El cuestionario: cómo guardarlo

Regla de oro: guarda lo cerrado en columnas tipadas (enum), no en texto libre ni en un JSON. Tu formulario ya manda códigos limpios (GT2Y, WEEKLY…); respétalos como enum y la base de datos te protege de basura. Guarda siempre la respuesta cruda y la categoría derivada — la cruda es la verdad, la derivada es una opinión que la organización puede sobrescribir.

Técnicas: arreglo, no cinco columnas

Como es selección múltiple (Saque, Chop, Backspin, Topspin), un text[] es lo natural. "Ninguna" se guarda como arreglo vacío '{}' — no como un valor más. Para tu scoring solo importa el conteo: array_length(techniques,1).

✓ Cruda + derivada, siempre las dos

Guardas experience, frequency, techniques… (lo que dijo) y también category_prov (lo que tu fórmula calculó) y category_final (lo que la organización ajustó). Si mañana cambias la fórmula, puedes recalcular todo desde lo crudo. Si solo guardas la categoría, perdiste la materia prima para siempre.

05Disponibilidad: ¿matriz?

Conceptualmente sí es una matriz: días (5) × bloques (7) = 35 casillas, cada una sí/no. La pregunta no es si se piensa como matriz, sino cómo se guarda. Tres opciones:

A · JSON / matriz 2D

Una columna jsonb con la rejilla.

Bien: simple de escribir.
Mal: no puedes preguntar fácil "¿quién puede el martes 9–11?" sin desempacar todo.

B · Bitmask (entero)

35 casillas → 35 bits en un bigint.

Bien: intersección de horarios = un AND bit a bit, ultrarrápido para el sorteo.
Mal: ilegible a ojo; rígido si cambian los bloques.

C · Tabla normalizada — recomendada

Una fila por bloque elegido en availability_slots. Es la opción flexible: consultas con SQL normal, soporta días/bloques variables, e índices la hacen rápida.

-- ¿Quiénes pueden el martes 19-ago a las 09:00?
select p.nickname
from availability_slots a
join registrations r on r.id = a.registration_id
join players p on p.id = r.player_id
where a.day = '2026-08-19' and a.block_start = '09:00';

-- ¿Cuántos bloques comparten dos jugadores? (clave para armar grupos)
select count(*) as bloques_en_comun
from availability_slots x
join availability_slots y
  on x.day = y.day and x.block_start = y.block_start
where x.registration_id = :jugador1
  and y.registration_id = :jugador2;

◆ Lo mejor de los dos mundos

Guarda en filas normalizadas (C) como fuente de verdad, y cuando corras el algoritmo de sorteo, derivas un bitmask (B) en memoria para que la intersección de horarios sea instantánea. No los guardas ambos en disco; el bitmask es un caché de cálculo.

06Power ranking: puntos estáticos

Tu decisión: un puntaje estático, no un ranking relativo (tipo Elo). Cada partido y cada logro suma o resta una cantidad fija, que se cierra en el momento y nunca se recalcula según contra quién ganaste o perdiste después. A cambio de no "premiar la sorpresa" automáticamente, ganas tres cosas que para tu torneo importan más: reglas claras y visibles que cualquiera entiende, fáciles de explicar, y triviales de auditar.

▸ El modelo en una caja

Ranking de un jugador = base de su categoría + Σ de todos sus eventos de puntos. Cada partido genera puntos por resultado (victoria / derrota, con o sin default); cada avance genera puntos por logro (pasar de grupos, ganar una llave, ser finalista, campeón…). Todo queda como filas en point_events. El número solo cambia con eventos nuevos: el pasado queda congelado.

¿Con cuántos puntos arranca cada categoría?

Recomendación: una sola escala para todos, pero con bases distintas por categoría. Así un avanzado siempre arranca por encima de un intermedio, y este por encima de un principiante, sin escalas separadas que comparar. Las bases están espaciadas para que cada categoría ocupe una banda: lo que ganas dentro de un torneo (decenas de puntos) no suele alcanzar para saltar de banda… salvo que arrases, que es justo la señal que quieres detectar.

✓ Bases escalonadas, no "límites duros"

Pensaste en topes (≤100 principiantes, ≤200 intermedios…). El choque: si los puntos se acumulan entre ediciones —y deben, para que sean historial— un tope fijo pelea contra esa acumulación. Mejor: bases separadas + acumulación libre + una regla de ascenso. El "tope" no lo pone un número congelado, lo pone que al cruzar la base de la categoría de arriba, asciendes. Mismo efecto que querías, sin frenar el progreso.

Puntos por partido (cualquier fase)

Lo que da o quita cada partido por sí solo, sin contar el avance. El margen pesa poco a propósito: así inventar un marcador apenas sirve —uno de tus dolores del torneo pasado.

Puntos por logro (progresión)

Se suman una sola vez al alcanzar el hito, además de los puntos del partido que lo produjo. Aquí aplico un multiplicador ligero por categoría (Principiante ×1.0, Intermedio ×1.15, Avanzado ×1.30) para "beneficiar ligeramente a las categorías superiores", igual que tu reparto del premio. El libro mayor, en código

Cerrar un partido = escribir las filas de point_events (una por jugador por resultado, más las de logro de quien avanzó) y refrescar el cache players.points.

-- Cerrar un partido de grupo: 1 fila por jugador
insert into point_events (player_id, edition_id, match_id, type, points) values
  (:ganador,  :ed, :m, 'WIN',  12),    -- victoria 2-0
  (:perdedor, :ed, :m, 'LOSS',  2);    -- derrota 0-2

-- Logro al clasificar 1.º en Avanzado (multiplicador ya aplicado)
insert into point_events (player_id, edition_id, type, points)
values (:ganador, :ed, 'GROUP_PASS', 20);

-- Refresca el ranking (cache). El número SIEMPRE es una suma, nunca un recálculo.
update players p set points = (
  select coalesce(sum(points),0) from point_events e where e.player_id = p.id
) where p.id = :ganador;

Ascensos y descensos: tu filtro anti-sandbagger

El problema que más te dolió —el "novato" que arrasó Principiantes siendo de nivel muy superior— el puntaje estático lo detecta solo. Regla:

  • Ascenso sugerido: si al cerrar la edición el total de un jugador alcanza o supera la base de la categoría de arriba, queda marcado para subir. Tu sandbagger de Principiantes terminaría arriba de 250 (base de Intermedio) tras un torneo ganado → señal clara y automática.
  • Descenso sugerido: quien lleva ediciones muy por debajo de su base (perdió casi todo) puede bajar, para que compita parejo.
  • Tú decides: es una sugerencia, no un cambio forzado. Se marca requires_review = true y ajustas category_final a mano, como ya hacías por WhatsApp.
-- Marca para revisión a quien cruzó la base de la categoría superior
update registrations r set requires_review = true
  from players p
 where p.id = r.player_id and r.edition_id = :edicion
   and p.points >= case r.category_final
                     when 'PRINCIPIANTE' then 250   -- base Intermedio
                     when 'INTERMEDIO'   then 450   -- base Avanzado
                     else 99999 end;

Jugadores nuevos sin historial

No tienen partidos, así que arrancan en la base de la categoría que les asignó el cuestionario —y ya. Sin números provisionales raros: si el formulario los pone en Intermedio, empiezan en 250 y el primer torneo los mueve desde ahí. Esa fila inicial se guarda como un evento BASE, para que el ledger cuadre desde el día uno.

-- Alta de un jugador nuevo: su base de categoría es el primer evento
insert into point_events (player_id, edition_id, type, points)
values (:nuevo, :ed, 'BASE',
  case :categoria when 'PRINCIPIANTE' then 100
                  when 'INTERMEDIO'   then 250
                  when 'AVANZADO'     then 450 end);

Si una persona cambia de categoría entre ediciones, no se le re-acredita la base: conserva sus puntos acumulados. La base solo entra una vez, al darse de alta.

07Bombos y algoritmo de sorteo

Con un puntaje por jugador, los bombos son un corte por bandas dentro de cada categoría. Ordenas por points descendente y partes en tantos bombos como tamaño tengan los grupos.

Ejemplo: categoría Avanzado, 16 jugadores, grupos de 4 → 4 bombos de 4. El Bombo 1 son los 4 de más puntos; nunca caen dos en el mismo grupo.

El sorteo, paso a paso

  1. Ordena por puntos y corta en bombos dentro de cada categoría. Guarda el número en registrations.seed_pot.
  2. Reparte un jugador de cada bombo por grupo. Cada grupo recibe exactamente uno del Bombo 1, uno del 2, etc.
  3. Aplica restricciones suaves al elegir cuál de cada bombo va a cuál grupo:
    • Evita dos de la misma carrera/facultad en un grupo (le da sabor "facultad vs facultad").
    • Exige que los del grupo compartan al menos un bloque de disponibilidad (sección 5), o el grupo no se puede jugar.
  4. Los nuevos sin historial entran con la base de su categoría. Como casi no se han movido del piso, márcalos para que la organización pueda reubicarlos tras ver sus primeros partidos.

Para 4–6 grupos esto se resuelve con una asignación tipo serpentina + un par de intercambios manuales. No necesitas un solver complejo; un heurístico con tus restricciones basta.

09Perfil del jugador (consultas)

Con este modelo, la página de perfil sale de unos cuantos joins.

-- Récord histórico (ganados / perdidos) de un jugador
select
  count(*) filter (where winner = :pid)                       as ganados,
  count(*) filter (where winner <> :pid)                      as perdidos,
  count(*)                                                     as total
from matches
where player_a = :pid or player_b = :pid;

-- Línea de tiempo de sus puntos (suma acumulada para una gráfica)
select created_at, type, points,
       sum(points) over (order by created_at) as puntos_acum
from point_events
where player_id = :pid
order by created_at;

-- Todas las ediciones que jugó, con categoría y bombo
select e.name, r.category_final, r.seed_pot, g.label as grupo
from registrations r
join editions e on e.id = r.edition_id
left join groups g on g.id = r.group_id
where r.player_id = :pid
order by e.starts_on;

10Orden de implementación

  1. Crea los enum y las tablas en Supabase (SQL de la sección 2). Activa RLS.
  2. Carga el histórico: edición pasada → players con su teléfono → matches desde las hojas.
  3. Aplica el reglamento de puntos sobre los matches en orden cronológico: escribe las filas de point_events que pueblan players.points.
  4. Conecta el formulario: al enviar, upsert por teléfono en players + insert en registrations + filas en availability_slots. Tu scoring.js llena category_prov.
  5. Enlace automático: al registrarse, el upsert por teléfono cae sobre el mismo player y recupera historial, puntos y categoría previa — sin pasos extra.
  6. Sorteo: corta bombos por points, asigna grupos con tus restricciones, guarda seed_pot y group_id.
  7. Cierre del torneo: captura resultados en matches, escribe sus point_events, aplica ascensos/descensos sugeridos y marca category_final. La siguiente edición arranca leyendo todo esto.

▸ En una frase

Guarda partidos y eventos de puntos, no puntajes finales; usa el teléfono para enlazar a la persona a través del tiempo; el ranking es una suma estática (base de categoría + eventos) y de ahí salen los bombos; y deja que el front resuelva las fotos a partir de los códigos de facultad y carrera.
